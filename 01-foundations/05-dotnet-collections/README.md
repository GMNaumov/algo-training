## Выбор начинается с операций

Коллекция хранит несколько элементов. Перед выбором спросите: нужен доступ по индексу, поиск по ключу, порядок поступления, уникальность или быстрый минимум? Одинаковое содержимое можно хранить разными способами с разной стоимостью операций.

Здесь n — число элементов. Для хеш-коллекций оценки предполагают подходящее хеширование и стоимость хеширования/сравнения ключа O(1).

| Тип | Для чего | Основная стоимость |
|---|---|---|
| Массив | фиксированное число позиций | индекс O(1), поиск значения O(n) |
| `List<T>` | растущий индексируемый список | добавление в конец амортизированно O(1), вставка в начало O(n) |
| `Dictionary<TKey,TValue>` | значение по уникальному ключу | поиск и обновление ожидаемо O(1), худший случай O(n) |
| `HashSet<T>` | проверка наличия и уникальность | ожидаемо O(1) для поиска и добавления |
| `Stack<T>` | последнее поступило — первое вышло | вершина O(1), добавление амортизированно O(1) |
| `Queue<T>` | первое поступило — первое вышло | извлечение O(1), добавление амортизированно O(1) |
| `LinkedList<T>` | изменения около известного узла | вставка и удаление узла O(1), поиск узла O(n) |
| `SortedSet<T>`, `SortedDictionary<TKey,TValue>` | упорядоченные ключи | поиск, вставка, удаление O(log n) |
| `PriorityQueue<TElement,TPriority>` | извлечение по минимальному приоритету | просмотр минимума O(1), вставка/извлечение O(log n) |

Каждая из этих коллекций хранит O(n) данных; точные накладные расходы различаются. Очередь с приоритетом не обещает порядок поступления при равных приоритетах. Её перечисление также не является последовательностью отсортированных извлечений.

## Пример: система заказов

Список заказов для показа по позиции удобно хранить индексируемо. Поиск заказа по номеру лучше обслуживать словарём. Уникальных клиентов — множеством. Печать чеков в порядке поступления — очередью. Срочные доставки с числовым приоритетом — приоритетной очередью.

Иногда нужны две структуры: список для порядка и словарь для поиска. Тогда важно согласованно обновлять обе; экономия времени оплачивается памятью и дополнительными правилами согласованности.

## Ошибки и практика

Нельзя считать поиск значения в списке постоянным только потому, что доступ по индексу постоянный. Нельзя рассчитывать на сортировку ключей обычного словаря. Изменение полей ключа, участвующих в равенстве и хеше, нарушает поиск.

**Практика.** Выберите коллекции для истории отмены, реестра уникальных email и ближайшего по времени события. Ответ: стек, множество, очередь с приоритетом. Объясните, какие операции сделали выбор естественным.

Справка: [выбор коллекции](https://learn.microsoft.com/en-us/dotnet/standard/collections/selecting-a-collection-class), [PriorityQueue](https://learn.microsoft.com/en-us/dotnet/api/system.collections.generic.priorityqueue-2). Доступность API проверяется для выбранной в будущем версии .NET.
