# Хеш-таблицы

[← К разделу](../README.md)

## Идея быстрого поиска

Хеш-таблица превращает ключ в число — хеш — и по нему выбирает место хранения. Это похоже на распределение заказов по ячейкам склада по номеру: сначала определяется подходящая ячейка, затем внутри неё проверяется точный ключ.

Разные ключи могут получить одно место: это коллизия. Корректная таблица умеет различать такие ключи, например хранит несколько записей в одной группе. Равенство хешей не доказывает равенство ключей. При этом равные ключи обязаны иметь одинаковый хеш.

Множество хранит только ключи, словарь — пары «ключ → значение». В словаре каждый ключ единственный; повторное поступление ключа нужно трактовать как обновление, ошибку или накопление по условию.

## Пример: подсчёт заказов клиента

Поступили клиенты: Анна, Борис, Анна, Анна, Борис. Храним число заказов по имени. После первого заказа Анна → 1. Затем Борис → 1. Третий заказ обновляет Анну до 2, четвёртый — до 3, пятый обновляет Бориса до 2.

Инвариант: после любого префикса потока словарь хранит точные частоты клиентов в этом префиксе. Каждый следующий заказ меняет ровно одну частоту, поэтому утверждение сохраняется. Для реальной системы именем ключевать рискованно: разные люди могут иметь одинаковое имя; нужен уникальный идентификатор.

## Сложность и ограничения

При подходящем распределении хешей поиск, добавление и удаление ожидаемо O(1), но худший случай O(n). Обработка n заказов ожидаемо O(n), память O(u), где u — число различных клиентов. Для длинных строк вычисление хеша и сравнение могут зависеть от длины ключа; эту стоимость учитывают отдельно.

Хеш-таблица не обеспечивает сортировку и поиск ближайшего ключа. Для диапазонов и упорядоченного обхода нужны другие структуры. Нельзя менять участвующие в хешировании свойства ключа после его помещения в таблицу.

**Практика.** Для товаров 7, 4, 7, 9, 4, 7 постройте таблицу частот: 7 → 3, 4 → 2, 9 → 1. Затем определите число различных товаров: 3. Объясните, почему одно множество даст второе число, но не частоты.
